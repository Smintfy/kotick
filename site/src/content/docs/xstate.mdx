`konat/xstate` connects XState v5 machines to konat. It exports all the functions of `@xstate/react`, with the same names and signatures. Thus, the change to your components is an import.

```ts
import { connect, defineFixtures, useMachine, useSelector } from 'konat/xstate';
```

The adapter uses the `xstate` and `@xstate/react` of your app. konat does not install them. Refer to [Requirements](/docs/install#requirements) for the versions.

## Quick start

1. Install `konat`, `xstate` and `@xstate/react`, and mount `<Konat />` once, as [Installation](/docs/install#quick-start) shows.
2. Import the XState hooks from `konat/xstate` instead of `@xstate/react`:

   ```diff
   - import { useMachine, useSelector, createActorContext } from '@xstate/react';
   + import { useMachine, useSelector, createActorContext } from 'konat/xstate';
   ```

3. If the app creates actors outside React, wrap them with `connect()`, as [Actors outside React](/docs/xstate#actors-outside-react) shows.
4. Use the app until the machine is in a second state. The panel lists every state, and an **R** mark shows each state that you visited.
5. Select a state in the panel. The components show that state in place. Select it again to release it.

## Actors outside React

Actors that you create outside React, for example in a module, need one more step. Wrap them with `connect()`:

```ts
import { createActor } from 'xstate';
import { connect } from 'konat/xstate';
import { sessionMachine } from '@/machines/session';

export const sessionActor = connect(createActor(sessionMachine).start(), { id: 'session' });
```

Use the actor that `connect()` returns everywhere in the app, for example with `useSelector(sessionActor, …)`.

## Prevent imports from @xstate/react

A component that imports a hook from `@xstate/react` continues to work, but the panel does not list its machine. To find these imports, add the `no-restricted-imports` rule to your linter. `konat/xstate` exports all the functions of `@xstate/react`, so the rule can block the full package. For ESLint:

```js
// eslint.config.js
export default [
  {
    rules: {
      'no-restricted-imports': [
        'error',
        {
          name: '@xstate/react',
          message: 'Import the XState hooks from konat/xstate, so that the panel lists the machine.',
        },
      ],
    },
  },
];
```

Oxlint has the same rule, with the same options.

## Nested and parallel states

A state of an XState machine can contain child states. A state without child states is a leaf. konat identifies a state by the dot path to its leaf, such as `payment.error`:

```
checkout
├── shipping
│   ├── standard
│   └── express
└── payment
    ├── editing
    ├── processing
    ├── error
    └── success
```

`checkout` is a parallel machine. A parallel machine is in one leaf of each region at the same time, for example `shipping.express` and `payment.error`. The panel shows the tree, and the keys of a fixture set are these leaf ids.

## Previews

The rules in [Previews](/docs/concepts#previews) apply. An XState machine adds these:

- **The preview is a real XState snapshot.** `matches()`, `hasTag()`, `can()` and `status` work as usual.
- **In a parallel machine, the regions that you did not touch keep their real state.**
- **The real actor continues to run.** Timers, invoked promises and callbacks continue in it.
- **A state without a recording or a fixture uses the live context.** konat logs a warning, because the live context often does not agree with the state. To give the state its own context, visit it in the app or write a [fixture](/docs/fixtures) for it.
- **Events from machines are blocked too.** The events that `sendTo()`, `forwardTo()` and delayed events send to a previewed actor go to the event log, as the events from the UI do.

## Child actors

Machines that a machine invokes or spawns are listed under their parent. You can see their state, but you cannot preview them in this version.

## The debug option

The hooks and `createActorContext` take one more option, `debug`. `connect()` takes the same object as its second argument. Use it to change how the panel shows an actor:

- To give an instance a name in the panel, set `label`. This helps when a machine has more than one instance.
- To give a machine an id that its definition does not have, set `id`. The panel, the recordings and the fixtures then find the machine by this id.
- To keep an actor out of konat, set `disabled: true`.

```ts
const [snapshot, send] = useMachine(checkoutMachine, { input, debug: { label: 'Checkout (modal)' } });
```

Give each machine an `id` in its definition when you can. Without one, konat makes an id from the states and the context keys of the machine. That id changes when you add or remove states or context keys. Refer to [The debug option](/docs/api#the-debug-option) for the type, and for what XState does with `debug` in production builds.

## Production builds

In production builds, the hooks of `konat/xstate` are the hooks of `@xstate/react`, and `connect()` returns the actor that you give it. The rest of the adapter is removed. With esbuild and Vite, the JavaScript that the app loads at startup is {costs.startup} (gzip) larger than the same app with `@xstate/react`. In development, a transition costs {costs.transition} more. Refer to [XState machines](/docs/production#xstate-machines) and [Performance in development](/docs/production#performance-in-development) in Production builds.

## How the adapter works

<ArchitectureDiagram caption="A component gets a proxy from useMachine(). The proxy calls the real actor and registers in the registry. The overlay selects a preview in the registry, and the proxy reads it." />

**The adapter gives your components a proxy of each actor.** The hooks call the hooks of `@xstate/react`, and return a proxy of the actor that they make. `connect()` does the same for an actor that you create outside React. The proxy sends each call to the real actor. During a preview, `getSnapshot()`, `subscribe()` and `send()` work differently.

**A preview is a snapshot that XState makes.** When you select a leaf, the registry keeps an override for that instance: the leaves and a context. The proxy gives the leaves and the context to `machine.resolveState()`, and returns that snapshot from `getSnapshot()` and to subscribers. The components render again with a real XState snapshot, so `matches()`, `hasTag()` and `can()` work. In a parallel machine, the regions that you did not select keep their current leaf. The live child actors are copied into the preview. The real actor does not know about the preview, and continues to run.

**Events go to a log during a preview.** `send()` on the proxy, and the internal send that `sendTo()`, `forwardTo()` and delayed events use, look for an override first. If there is one, the event goes to the event log of the panel, not to the actor.
