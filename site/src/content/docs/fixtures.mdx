Fixtures give context to states that you have not recorded yet, such as an error after a slow request.

## Define fixtures

Put them in a file of their own, and give `<Konat />` a loader for that file:

```ts
// src/debug/fixtures.ts
import { defineFixtures } from 'konat/xstate';
import { checkoutMachine } from '@/machines/checkout';

const items = [{ id: 'sku_1', name: 'Linen tote', price: 2400, qty: 2 }];
const card = { number: '4242 4242 4242 4242', expiry: '12/30', cvc: '123' };

export default [
  defineFixtures(checkoutMachine, {
    'payment.error': { context: { items, card: { ...card, number: '4000 0000 0000 0002' }, error: 'Card declined' } },
    'payment.success': { context: { items, card, receiptId: 'rcpt_123' } },
  }),
];
```

`checkoutMachine` is the machine of the checkout demo. To see it, open `machine.ts` in the Code tab of the [checkout example](/docs/examples#checkout).

The loader has a development condition. The condition removes the fixtures, and the import, from production builds. Use the condition of your bundler.

In Vite:

```tsx
import { Konat } from 'konat';

const fixtures = import.meta.env.DEV ? () => import('@/debug/fixtures') : undefined;

export function DevTools() {
  return <Konat fixtures={fixtures} />;
}
```

In Next.js and other bundlers:

```tsx
import { Konat } from 'konat';

const fixtures = process.env.NODE_ENV !== 'production' ? () => import('@/debug/fixtures') : undefined;

export function DevTools() {
  return <Konat fixtures={fixtures} />;
}
```

Do not use `process.env.NODE_ENV` in Vite. A default Vite app does not have the Node.js types, thus TypeScript does not know `process`. In Next.js, put `'use client'` at the top of the file. Refer to [Next.js](/docs/nextjs).

The examples import from `src` through the `@/` alias. Next.js sets this alias, but Vite does not. In Vite, add the alias to `paths` in your TypeScript config and to `resolve.alias` in `vite.config.ts`, or use relative imports.

## How fixtures apply

- The keys are leaf ids. TypeScript checks them against the states of the machine, and `context` against the context type of the machine.
- A fixture set applies to each instance of its machine, also to copies from `machine.provide()`, and to machines that `debug.id` renames.
- The loader runs after the page loads. Previews that started before it finished change to the fixture when it arrives. Such a preview logs the warning about the live context only if the loader gives no fixture for it.
- In a parallel preview, the first leaf that has a fixture gives the context: the leaves you selected, in sequence, then the leaves of the other regions.
- You can give an array of sets in place of a loader. Then the sets are in your main bundle, also in production. Use a loader with a development check to keep them out.
