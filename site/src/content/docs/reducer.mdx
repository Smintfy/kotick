If a component keeps a union of states in `useReducer`, declare the reducer as a machine with `kotick/reducer`. kotick then lists every state of the machine and previews any of them in place.

```ts
import { defineFixtures, defineReducerMachine, useMachineReducer } from 'kotick/reducer';
```

An app that uses only `kotick/reducer` does not need `xstate` or `@xstate/react`. Install `kotick` alone.

## Quick start

1. Declare the reducer as a machine with `defineReducerMachine`. [Convert a switch reducer](/docs/reducer#convert-a-switch-reducer) gives the steps.
2. In the component, call `useMachineReducer(machine, initial)` in place of `useReducer(reducer, initial)`.
3. Mount `<Kotick />` once, as the [quick start](/docs/install#quick-start) shows.
4. Use the app until the component is in a second state. The panel lists every state, and an **R** mark shows each state that you visited.
5. Select a visited state in the panel. The component shows that state in place, with the data of your visit.

A state that you did not visit is greyed out until it has a fixture. To start the fixtures file, select a visited state and use **Copy context**. The JSON is the fixture of that state. For a state that is hard to visit, write the object by hand. [Previews](/docs/reducer#previews) explains why a state needs data.

## Convert a switch reducer

A `switch` reducer has one branch for each event. A machine has one handler for each state and event.

1. Make the state a union with one key that holds the name of the state. That key is the `discriminant`.
2. For each branch of the `switch`, write a handler under each state in which the event is valid. Leave the handler out of the other states, and they ignore the event.
3. Move each `useEffect` that depends on the name of the state to the `effect` of that state. Change `dispatch` to `send`, and read props and hook values through `input()`.
4. Change `useReducer(reducer, initial)` to `useMachineReducer(machine, initial)`.
5. Keep the tests of the old reducer, and run them on `machine.reducer`.

This search box accepts `SEARCH` while it is not loading, and `RESOLVE` and `CANCEL` only while it is loading. A `useEffect` starts the search when the state is `loading`:

```tsx
// src/components/search-box.tsx
import { useEffect, useReducer } from 'react';
import { useSearchClient } from '@/lib/search-client';

type SearchState =
  | { status: 'idle' }
  | { status: 'loading'; query: string }
  | { status: 'ready'; query: string; hits: string[] };

type SearchEvent = { type: 'SEARCH'; query: string } | { type: 'RESOLVE'; hits: string[] } | { type: 'CANCEL' };

function reducer(state: SearchState, event: SearchEvent): SearchState {
  switch (event.type) {
    case 'SEARCH':
      return state.status === 'loading' ? state : { status: 'loading', query: event.query };
    case 'RESOLVE':
      return state.status === 'loading' ? { status: 'ready', query: state.query, hits: event.hits } : state;
    case 'CANCEL':
      return state.status === 'loading' ? { status: 'idle' } : state;
  }
}

export function SearchBox({ onHits }: { onHits(hits: string[]): void }) {
  const search = useSearchClient();
  const [state, dispatch] = useReducer(reducer, { status: 'idle' });

  useEffect(() => {
    if (state.status !== 'loading') return;
    const controller = new AbortController();
    void search(state.query, controller.signal).then((hits) => {
      dispatch({ type: 'RESOLVE', hits });
      onHits(hits);
    });

    return () => controller.abort();
  }, [state, search, onHits]);

  return (
    <input
      value={state.status === 'idle' ? '' : state.query}
      onChange={(event) => dispatch({ type: 'SEARCH', query: event.target.value })}
    />
  );
}
```

As a machine, each state lists the events that it accepts. The search moves from the `useEffect` to the `effect` of `loading`, and reads `search` and `onHits` through `input()`:

```ts
// src/machines/search.ts
import { defineReducerMachine } from 'kotick/reducer';

export type SearchState =
  | { status: 'idle' }
  | { status: 'loading'; query: string }
  | { status: 'ready'; query: string; hits: string[] };

export type SearchEvent = { type: 'SEARCH'; query: string } | { type: 'RESOLVE'; hits: string[] } | { type: 'CANCEL' };

export interface SearchInput {
  search(query: string, signal: AbortSignal): Promise<string[]>;
  onHits(hits: string[]): void;
}

export const searchMachine = defineReducerMachine<SearchState, SearchEvent, SearchInput>()({
  id: 'search',
  discriminant: 'status',
  states: {
    idle: { on: { SEARCH: (_state, event) => ({ status: 'loading', query: event.query }) } },
    loading: {
      on: {
        RESOLVE: (state, event) => ({ status: 'ready', query: state.query, hits: event.hits }),
        CANCEL: () => ({ status: 'idle' }),
      },
      effect: (state, send, input) => {
        const controller = new AbortController();
        void input()
          .search(state.query, controller.signal)
          .then((hits) => {
            send({ type: 'RESOLVE', hits });
            input().onHits(hits);
          });

        return () => controller.abort();
      },
    },
    ready: { on: { SEARCH: (_state, event) => ({ status: 'loading', query: event.query }) } },
  },
});
```

The component then calls `useMachineReducer` in place of `useReducer`, and has no `useEffect`. [Use the machine](/docs/reducer#use-the-machine) shows the new component.

## Define a machine

A machine follows five rules. TypeScript checks rules 1 and 3, and each fixture of rule 2. The panel greys out each state that does not have data yet. Rules 4 and 5 are yours to follow.

1. **One key, the `discriminant`, holds the name of the state.** `states` has one entry for each name. TypeScript checks the entries against your union, so a missing state, an extra state, and a misspelled event do not compile.
2. **A state needs data before you can preview it.** A visit in the app records its state object. `defineFixtures` takes a state object for each state that you list, and each fixture is a whole state of its own name. To make the fixtures file fail when a state has no fixture, check the set with `satisfies CompleteFixtures<typeof machine>`. See [Define fixtures](/docs/fixtures#define-fixtures).
3. **Transitions are per state and per event.** A handler gets the state object of its state and the event of its type, and returns the next state. A state ignores the events that it does not list, and a handler that returns `state` ignores its event. A handler gets no input, because it must be pure, as a reducer is. `machine.reducer` is the plain reducer, for unit tests.
4. **Effects are per state.** An `effect` gets `(state, send, input)`, and can return a cleanup.
   - The effect starts after the commit that enters its state.
   - The cleanup runs after the commit that leaves the state, and when the component unmounts. After the cleanup, `send` does nothing.
   - A transition that keeps the name of the state keeps the effect running. A batch of events that leaves the state and enters it again runs the cleanup and starts the effect again.
   - React's rules for effects apply. When the component mounts, StrictMode starts the effect, runs its cleanup, and starts it again.
   - `input()` returns the newest input that the component gave the hook. So an effect can call the router, a client from React context, or a callback prop.
5. **Async work is in the machine.** Start a request in the `effect` of a state, and give its result to `send`. kotick never blocks the `send` of a machine effect.

   During a preview, kotick blocks each event that the component dispatches, and does not replay the events after the release. So a click handler that dispatches `SUBMIT`, awaits `submitOrder()`, and then dispatches `RESOLVE` loses `RESOLVE` if a preview is open when the response comes. After the release, the machine stays in `loading`. A component `useEffect` that dispatches the result has the same problem, and it also runs for a previewed state.

These rules are public API. A change to a rule, to the arguments of a handler or an effect, or to the order of start and cleanup is a breaking change. While kotick is 0.x, a breaking change bumps the minor version, and never the patch version.

## Use the machine

`useMachineReducer(machine, initial, options?)` returns `[state, dispatch]`, as `useReducer` does. `initial` is the first state, or a function that returns it.

```tsx
// src/components/search-box.tsx
import { useMachineReducer } from 'kotick/reducer';
import { useSearchClient } from '@/lib/search-client';
import { searchMachine } from '@/machines/search';

export function SearchBox({ onHits }: { onHits(hits: string[]): void }) {
  const search = useSearchClient();
  const [state, dispatch] = useMachineReducer(searchMachine, { status: 'idle' }, { input: { search, onHits } });

  return (
    <input
      value={state.status === 'idle' ? '' : state.query}
      onChange={(event) => dispatch({ type: 'SEARCH', query: event.target.value })}
    />
  );
}
```

`options.input` is the value that `input()` returns in the effects. Declare its type as the third type argument of `defineReducerMachine`, and the hook then requires it. For `searchMachine`, an input without `onHits` does not compile. The object is new on each render, but the search does not restart, because the effect reads the input through `input()` when it needs it. A new input never restarts an effect.

`RESOLVE` comes from `send`, so a preview that is open when the response comes does not block it. The real state goes to `ready`, and the release shows it.

`options.debug` takes `{ label, disabled }`. `label` is the name of the instance in the panel, and `disabled: true` keeps the instance out of kotick. kotick reads `debug` only in development builds.

Each component that calls the hook is one instance. Do not give `machine.reducer` to `useReducer` in a component. The state then changes, but no effect runs, and the panel does not list the component.

## Previews

The rules in [Previews](/docs/concepts#previews) apply. When you select a state, the component gets a state object of that state in place of the real one. It does not mount again.

The state object comes from a recording or a fixture of the selected state. The live state object fits only the state that the machine is in, so **Live** is available only for that state. You cannot preview another state until it has a recording or a fixture. Until then, the panel greys out the state and names it under **States**.

During a preview, the panel logs the events that the component dispatches, and they do not reach the machine. The effect of the real state continues to run, and the previewed state runs no machine effect. When you release the preview, the component shows the real state at that time.

kotick checks only the name of the state. A recording from before you added a field to a state does not have that field.

## Production builds

Production builds keep `defineReducerMachine` and `useMachineReducer` as a small runtime around React's `useReducer` and `useEffect`. The runtime runs your transitions and effects. The bundler removes the registry, the panel, the recordings, and the fixtures. `defineFixtures` stays only if production code imports it. [Choose an adapter](/docs/concepts#choose-an-adapter) shows the size of the runtime.

- A server component or a route handler can import a machine file and call `machine.reducer`. Only `useMachineReducer` is client code.
- The runtime calls only built-in functions that every browser that runs React has, such as `Object.freeze` and `Object.is`. After the bundler removes the development code, the runtime uses only ES2020 syntax. A build for an older browser must transpile `kotick`.
- The development code in the same files uses ES2021 syntax, such as `??=`. The bundler must parse that code before it removes it.

## Remove kotick

To remove kotick, write a reducer that picks the handler by the name of the state and the type of the event, and a `useEffect` that runs the effect of the state. The handlers and the effects are plain functions, so they move as they are.
