In production builds, `<Konat />` renders nothing, the hooks are the hooks of `@xstate/react`, and the registry, the overlay and the adapter are removed from the bundle. You do not have to remove the overlay or change the imports before a release. In a test runner, `NODE_ENV` is `"test"`, so konat stays on. Refer to [Tests](/docs/tests).

This needs a bundler that replaces `process.env.NODE_ENV` with `"production"`. Vite, Next.js (webpack and Turbopack) and React Router do this. With esbuild, add `--define:process.env.NODE_ENV='"production"'`. The package sets `"sideEffects": false`, so the bundler can remove the modules that nothing uses.

The repository has a check for this (`pnpm check:bundles`). It packs the package as npm publishes it, builds an app with each of these bundlers, and looks for debug code in the output. With esbuild and Vite, the JavaScript that the app loads at startup is {costs.startup} (gzip) larger than the same app with `@xstate/react`.

Put a development check on the fixtures loader, as in the [Fixtures](/docs/fixtures) examples. Without the check, the fixtures are a chunk that the production app never loads, but the build still makes it.

## Performance in development

When the panel is closed, the overlay itself costs almost nothing. The adapter costs a small amount: it registers each actor, records its context, and passes snapshots through a proxy. These numbers are from the benchmarks in `bench/`, in jsdom with StrictMode. Compare the rows, not the absolute times.

| Work | `@xstate/react` | `konat/xstate` |
|---|---|---|
| A transition that renders a `useMachine` component again | 27 µs | 34 µs |
| Mount and unmount 50 rows, each with `useMachine` | 1.0 ms | 2.1 ms |
| 100 events to an actor outside React (`connect()`) | 0.17 ms | 0.22 ms |

Thus, a transition costs {costs.transition} more, a mount approximately 22 µs more, and an event to a `connect()`ed actor less than 1 µs more. Production builds do not have this cost.
