In production builds, `<Konat />` renders nothing, and the registry and the overlay are removed from the bundle. Each adapter keeps a different part of itself, as [Reducer machines](/docs/production#reducer-machines) and [XState machines](/docs/production#xstate-machines) describe. You do not have to remove the overlay or change the imports before a release. In a test runner, `NODE_ENV` is `"test"`, so konat stays on. Refer to [Tests](/docs/tests).

This needs a bundler that replaces `process.env.NODE_ENV` with `"production"`. Vite, Next.js (webpack and Turbopack) and React Router do this. With esbuild, add `--define:process.env.NODE_ENV='"production"'`. The package sets `"sideEffects": false`, so the bundler can remove the modules that nothing uses.

The repository has a check for this (`pnpm check:bundles`). It packs the package as npm publishes it, builds an app with each of these bundlers, and looks for debug code in the output. The sections below give the size that each adapter adds to the JavaScript that the app loads at startup.

Put a development check on the fixtures loader, as in the [Fixtures](/docs/fixtures) examples. Without the check, the fixtures are a chunk that the production app never loads, but the build still makes it.

## Reducer machines

The transitions and the effects of a [reducer machine](/docs/reducer) are code of your app, so production builds keep `defineReducerMachine` and `useMachineReducer`. They are a small runtime around React's `useReducer` and `useEffect`. With esbuild and Vite, the JavaScript that the app loads at startup is {costs.reducerStartup} (gzip) larger than the same app written with `useReducer`, a `switch` and `useEffect`. The registry, the panel, the recordings and the fixtures are removed. `defineFixtures` stays only if production code imports it.

A server component or a route handler can import a machine file, because only `useMachineReducer` is client code. The rules of a machine are public API, and you can remove konat without a change to your handlers and effects. Refer to [Production builds](/docs/reducer#production-builds) in useReducer.

## XState machines

The hooks of `konat/xstate` are the hooks of `@xstate/react`, and `connect()` returns the actor that you give it. The rest of that adapter is removed. XState gets the `debug` option of the hooks, keeps it in `actor.options`, and does nothing with it. With esbuild and Vite, the JavaScript that the app loads at startup is {costs.startup} (gzip) larger than the same app with `@xstate/react`. Refer to [Production builds](/docs/xstate#production-builds) in XState.

## Performance in development

When the panel is closed, the overlay itself costs almost nothing. The XState adapter costs a small amount: it registers each actor, records its context, and passes snapshots through a proxy. These numbers are from the benchmarks in `bench/`, in jsdom with StrictMode. Compare the rows, not the absolute times.

| Work | `@xstate/react` | `konat/xstate` |
|---|---|---|
| A transition that renders a `useMachine` component again | 27 µs | 34 µs |
| Mount and unmount 50 rows, each with `useMachine` | 1.0 ms | 2.1 ms |
| 100 events to an actor outside React (`connect()`) | 0.17 ms | 0.22 ms |

Thus, a transition costs {costs.transition} more, a mount approximately 22 µs more, and an event to a `connect()`ed actor less than 1 µs more. Production builds do not have this cost.
