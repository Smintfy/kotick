## Previews

These limits apply to both adapters:

- **Releasing shows the real state at that time.** The real machine kept running during the preview.
- **After a reload, recordings have no functions.** kotick writes the recordings to `sessionStorage` as JSON, which has no functions.

### Reducer machines

- **You cannot preview a state that has no recording and no fixture.** The live state object fits only the state that the machine is in. The panel greys out the other states until you visit them or write a [fixture](/docs/fixtures#define-fixtures) for them.
- **kotick drops the events that the component dispatches during a preview.** It does not replay them after the release. A click handler or a component `useEffect` that dispatches the result of a request loses that event if a preview is open when the response comes. Send the result from the `effect` of the state instead, as rule 5 in [Define a machine](/docs/reducer#define-a-machine) shows.
- **The effect of the previewed state does not run.** The effect of the real state continues to run, and kotick never blocks its `send`.
- **kotick checks only the name of the state.** A recording or a fixture without a field of the state still previews, and the component gets the object without that field.

### XState machines

- **Effects in the machine do not run during a preview.** Invoked actors, delayed transitions, and entry actions of the previewed state do not start. Effects in components that react to the state, such as a `useEffect` that depends on `snapshot.value`, do run.
- **Child actors are read-only.** You can see them, but you cannot preview them. A preview keeps the live children in `snapshot.children`, so components that read them continue to work. This copy of the live children is experimental.
- **Around a preview, an observer can get a snapshot one more or one less time than with `@xstate/react`.** Without a preview, an observer given to a hook gets the same calls as with `@xstate/react`. A few rare sequences around a preview, such as a Fast Refresh edit or an `<Activity>` that hides the component, can give it one more, one less, or a later snapshot. The number of `complete` and `error` calls stays the same. kotick builds the preview again when its live children change, when fixtures load, or when an edit adds a region, and the observer gets each new preview.

## Recordings

kotick records context to show it in [previews](/docs/concepts#context-for-a-preview). It keeps the recordings in memory, and writes a copy to `sessionStorage`, so that they are still there after a reload. These limits apply:

- **50 sets of leaves for each machine.** When a machine gets to a 51st set of leaves, kotick removes the oldest recording of that machine.
- **100,000 characters for each context.** kotick keeps a larger context in memory only, so it is not there after a reload.
- **1,000,000 characters in `sessionStorage` for all machines.** Over this limit, kotick writes only the newest recordings. It keeps the others in memory until the page reloads, and shows a [warning](/docs/troubleshooting#console-warnings) once for each machine.

## The panel

- **The panel lists only the machines that an adapter registers.** [A machine is missing from the panel](/docs/troubleshooting#a-machine-is-missing-from-the-panel) lists the causes.
- **You cannot select a history state.**
- **The arrow keys move through the leaves that show.** Compound and parallel states cannot get focus, so only a click collapses or expands them. The arrow keys skip the leaves of a collapsed state.
- **The state tree shows the fixtures of the first instance of a machine id.** When `debug.id` gives two different machines the same id, the instance of the second machine can get other fixtures.
- **A transform on `body` moves the overlay.** If `body` has a `transform`, a `filter`, or `contain`, it becomes the containing block of the overlay. Use `portalTarget={document.documentElement}` on such pages.
